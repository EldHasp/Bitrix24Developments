# Локальное приложение + активити БП (облако Битрикс24)

Практический чеклист по опыту портала `braincon.bitrix24.ru` (2026-07).  
Пример реализации: [`apps/lead-rating-api`](../apps/lead-rating-api/README.md).

## Зачем так, а не маркетплейс-«Вебхук»

Сторонние активити вроде `[REST Активити Б24] Вебхук` часто:

- шлют **FormData**, а не JSON;
- требуют JSONPath под чужой формат ответа;
- ставят **долгий период ожидания** (минуты) — неудобно для синхронного расчёта.

Своё активити через `bizproc.activity.add` + `bizproc.event.send` возвращает результат за секунды и даёт нормальные поля входа/выхода.

## Серверное vs статичное

| Тип | Когда |
|-----|--------|
| **Серверное** | Нужен HTTPS-handler: установка, активити БП, роботы, события. **Наш случай.** |
| **Статичное** | Только HTML/JS в слайдере через `BX24`, без серверного handler. Для активити БП **не подходит**. |

## Где что лежит в UI (важно)

Раздел **«Готовые сценарии → Другое»** — это **только создание**, не список.

| Что ищете | Куда |
|-----------|------|
| Создать локальное приложение | Приложения → **Разработчикам** → **Готовые сценарии** → **Другое** → **Локальное приложение** |
| Список уже созданных (приложения + вебхуки вместе) | Приложения → **Разработчикам** → вкладка **«Интеграции»** (`/devops/list/`) |
| Открыть/править своё приложение | В **Интеграциях** найти по **названию меню** (не по слову «вебхук») → открыть |
| Пункт левого меню | Появляется после сохранения (название из поля «Название пункта меню»). Если нет — открывайте из карточки приложения |
| Активити в БП | Дизайнер БП нужной сущности → **Действия приложений** → имя активити |

Прямые URL портала:

- хаб: `https://<портал>/devops/`
- список интеграций: `https://<портал>/devops/list/`

В **Интеграциях** вперемешку вебхуки и локальные приложения. Локальное приложение называется как **пункт меню**, а не «Входящий вебхук».

## Поля формы локального приложения

| Поле | Что ставить |
|------|-------------|
| Тип | **Серверное** |
| Путь обработчика | URL UI/handler приложения (открытие из меню / «Перейти к приложению») |
| Путь для первоначальной установки | URL install (кнопка **«Переустановить»** и первая установка) |
| Использует только API | Обычно **выкл**, если нужен пункт меню и слайдер |
| Название пункта меню | Человекочитаемое имя (оно же в списке интеграций и в левом меню) |
| Права | Минимум для активити: **`crm`** + **`bizproc`**. Без `bizproc` регистрация активити не взлетит |

После первого сохранения появляются `client_id` / `client_secret` и кнопки **«Перейти к приложению»** / **«Переустановить»**.  
**Не коммитить и не светить `client_secret` в чатах/скринах.**

### Handler vs Install — разные URL

Рекомендуемая схема (как в lead-rating-api):

| Поле | Пример |
|------|--------|
| Обработчик | `https://…/bitrix/handler` |
| Установка | `https://…/bitrix/install` |

Оба могут жить на одном сервисе.  
**Активити БП** регистрируется с отдельным `HANDLER`, например `https://…/bitrix/activity` — его Битрикс вызывает при выполнении шага БП (это не то же самое, что «путь обработчика» в карточке приложения, но **домен должен совпадать** с доменом локального приложения).

## Auth: почему «Нет auth от Битрикс»

Частая ситуация: жмёте **«Перейти к приложению»** → iframe открывает handler **GET-ом без** `auth[access_token]` → сервер отвечает «нет auth».

Как Битрикс реально передаёт доступ:

1. Иногда POST/query: `auth[access_token]`, `auth[domain]` или плоско **`AUTH_ID` + `DOMAIN`**.
2. Часто при открытии UI — **только через JS `BX24.getAuth()`** внутри iframe.

**Рабочий паттерн handler/install-страницы:**

1. Если в запросе уже есть token+domain → сразу `bizproc.activity.add` / нужная логика.
2. Иначе отдать HTML с `//api.bitrix24.com/api/v1/`, в `BX24.init` взять `BX24.getAuth()`, вызвать свой backend (например `POST /bitrix/register-from-bx24`), затем при установке — `BX24.installFinish()`.

Кнопки:

| Кнопка | Когда жать |
|--------|------------|
| **Переустановить** | Регистрация/обновление активити → экран «Готово» |
| **Перейти к приложению** / пункт меню | Справка по приложению (не «Готово»): ссылки на Интеграции и кнопка перерегистрации активити |

Карточка с «Переустановить» — только в **Интеграциях** / ` /devops/edit/application/<id>/ `, не в пункте меню.
## Регистрация активити (REST)

Только в контексте **приложения** (токен локального приложения), не входящим вебхуком.

1. При установке/переустановке: `bizproc.activity.delete` (если уже было) → `bizproc.activity.add`.
2. Обязательно для возврата значений в БП:
   - `USE_SUBSCRIPTION: 'Y'`
   - `RETURN_PROPERTIES` (например `RatingEnumId`, `RatingLabel`, …)
3. При выполнении шага БП Битрикс POST-ит на `HANDLER` активити (`event_token`, `document_id`, `properties`, `auth`).
4. Приложение считает результат и вызывает **`bizproc.event.send`** с `event_token` + `return_values`.
5. HTTP-ответ handler’у активити можно отдать сразу `200`; продолжение БП ждёт `event.send`, а не тело ответа.

Ограничение сущности (пример — только лиды):

```text
DOCUMENT_TYPE: ['crm', 'CCrmDocumentLead', 'LEAD']
FILTER.INCLUDE: [['crm', 'CCrmDocumentLead', 'LEAD']]
```

Входные `PROPERTIES`: `string` / `select` / `bool` и т.д.  
В дизайнере БП пользователь мапит поля документа или оставляет пустыми (если handler сам читает лид через `crm.lead.get`).

## Проверка «всё ок»

1. **Переустановить** → страница «Готово», код активити в тексте.
2. В левом меню есть пункт с названием приложения (не обязательно, но признак).
3. В дизайнере БП лида в **Действиях приложений** есть пункт вида  
   `[Имя приложения] Имя активити`.
4. Тестовый прогон на лиде: лог БП / поле «Рейтинг лида» обновилось (если включена запись в CRM).

Если пункта в БП нет: ещё раз **Переустановить**, закрыть/открыть дизайнер шаблона.

## Типичные ошибки

| Симптом | Причина / что сделать |
|---------|------------------------|
| На плитке «Другое» нет списка приложений | Это экран создания; список — вкладка **Интеграции** |
| В Интеграциях только «вебхуки» | Ищите по **названию меню**; локальное приложение не называется «Входящий вебхук» |
| «Нет auth от Битрикс» | Нет POST-auth; нужен BX24-bootstrap на handler/install |
| Активити нет в БП | Не отработала регистрация / нет права `bizproc` / не тот `DOCUMENT_TYPE`/`FILTER` |
| Handler активити с другого домена | Битрикс требует тот же домен, что у локального приложения |
| Долгое ожидание шага БП / «висит» на активити | Чаще всего **нет `access_token` в POST активити** → не вызван `bizproc.event.send`. См. раздел OAuth ниже |
| 405 / JSON вместо UI при открытии приложения | В карточку приложения ошибочно поставили URL **`/bitrix/activity`** вместо handler/install |
| Apex Layero странно отвечает, preview ок | Для Битрикс URL использовать **preview**-домен (`….preview.layero.ru`) |
| После деплоя снова «нет токена» / БП висит | Эфемерный OAuth-файл на Layero. Нужен устойчивый env: **отдельный** `BITRIX_WEBHOOK_URL` или `BITRIX_REFRESH_TOKEN` (см. ниже) |
| В Интеграциях нет только что созданного вебхука | Список — вкладка **Интеграции** (`/devops/list/`), не «Другое». Обновить страницу; искать «Входящий вебхук» |
| Перегенерировали вебхук — отвалились другие системы | «Перегенерировать» **убивает** старый URL. Для нового сервиса создавайте **отдельный** вебхук |

## Auth для активити БП: OAuth + устойчивый запас на Layero

### Важное заблуждение

Пользователь **не передаёт входящий вебхук** приложениям других разработчиков / чужим порталам — и правильно.  
Приложения Маркета работают на **OAuth**: `client_id` / `client_secret` + токены портала на сервере разработчика (по `member_id`).

Локальное серверное приложение — та же OAuth-модель для «правильной» схемы.  
`BITRIX_WEBHOOK_URL` в Layero — **только технический запас для одного вашего портала** (чтобы переживать деплои без открытия меню). При раздаче другим порталам вебхук клиентов **не** собирают.

### OAuth (основная модель приложения)

| Что | Откуда | Куда |
|-----|--------|------|
| **Код приложения** (`local.…`) | карточка локального приложения | env `BITRIX_CLIENT_ID` |
| **Ключ приложения** | та же карточка | env `BITRIX_CLIENT_SECRET` |
| `access_token` / `refresh_token` | `BX24.getAuth()` при открытии меню | `POST /bitrix/save-auth` → файл на сервере (до деплоя) |

### Устойчивость после деплоя Layero (обязательно на практике)

На Layero (free `node_web`) **нет постоянного диска**: `data/bitrix-oauth.json` стирается при каждом деплое → без запаса снова «висит» БП.

**Рекомендуемый запас (рабочий на braincon, 2026-07):**

1. Создать **отдельный** входящий вебхук (не тот, что уже в Google Sheets / других системах).
2. Права только **crm** + **bizproc**.
3. Название в карточке поменять на понятное (открыть в Интеграциях → поле «Название»), напр. `lead-rating-api (Layero)`.
4. URL вебхука → Layero env `BITRIX_WEBHOOK_URL` (секрет, не в git/чат).
5. После добавления env — **redeploy**.
6. **Не жать «Перегенерировать»** на старых вебхуках — старый URL сразу мёртв для всех потребителей.

Альтернатива: `BITRIX_REFRESH_TOKEN` + `BITRIX_DOMAIN` (со страницы приложения после save-auth).

Проверка: `GET /bitrix/debug/oauth-status` → `hasWebhook: true` и/или `hasEnvRefresh: true`.  
Список вебхуков/приложений: `https://<портал>/devops/list/`.

### Корневая причина зависания БП (подтверждено 2026-07)

1. Битрикс **доходит** до `POST /bitrix/activity` (`event_token`, `leadId`, свойства есть).
2. Но в теле часто **нет рабочего `access_token`** (`hasAuth: false`; бывают `domain`, `application_token`, `member_id`).
3. Без OAuth/webhook нельзя вызвать `crm.lead.get` / `crm.lead.update` / **`bizproc.event.send`**.
4. БП ждёт `event.send` → шаг «висит».

Отладка: `GET /bitrix/debug/last-activity` (`hasAuth`, `authSource`, `canCallRest`, `logMessage`, `resolveError`, `durable`).

### Рабочая схема (как в `lead-rating-api`)

1. Env: `BITRIX_CLIENT_ID`, `BITRIX_CLIENT_SECRET`, `PUBLIC_BASE_URL` (preview), плюс **`BITRIX_WEBHOOK_URL`** (или refresh).
2. Меню (`/bitrix/handler`): `BX24.init` → `saveAuth` + перерегистрация активити.
3. Активити: `resolvePortalAuth` (request → file → refresh file/env) → REST; иначе webhook.
4. Писать «Рейтинг лида» **только если enum ID изменился** (иначе цикл БП «при изменении»).
5. **Сначала** `bizproc.event.send`, **потом** HTTP `200`.
6. БП-шаблон: автозапуск **при создании** и **при изменении**; без безусловной записи отладочных полей каждый раз.

### Три URL — не путать

| URL | Куда вписывать |
|-----|----------------|
| `/bitrix/handler` | «Путь вашего обработчика» в карточке приложения |
| `/bitrix/install` | «Путь для первоначальной установки» |
| `/bitrix/activity` | **только** в `bizproc.activity.add` → `HANDLER` (в карточку приложения **нельзя**) |

### Bool-свойства активити

Пустые/кривые значения `WriteToLead` в БП: парсить через `propFlag(value, defaultYes=true)` — пусто → **Да**.  
Критерии всегда читаются с лида (флага AutoFromLead больше нет).

### Период ожидания в дизайнере БП

Ставить **10+ мин** как страховку. При рабочем `event.send` ответ обычно за секунды.

### Автозапуск при создании/изменении лида

Шаблон БП: параметры запуска → **при создании** и **при изменении**.  
Активити рейтинга пишет поле **только при смене значения**: иначе `crm.lead.update` снова запускает БП «при изменении».

Не пишите в том же БП каждый раз отладочное поле (`avg | label`) без условия — это тоже триггерит «изменение».

### Таблица весов из Битрикс (не из деплоя)

Активити получает конфиг только через свойства. Откуда строку подставили — **неважно** (глобальная константа или константа шаблона).

| Свойство | Смысл |
|----------|--------|
| **Таблица весов (JSON)** / `ScoringTable` | какие UF и веса 1…4 |
| **Конфиг рейтинга (JSON)** / `RatingConfig` | `field` + `thresholds` (avg → enumId/label) |

1. В константах — JSON (чертежи: `bp-scoring-table.json`, `bp-rating-config.json`).
2. В дизайнере: вставить константы в свойства активити (сырая строка, **без** `jsonval`).
3. Смена списков / поля рейтинга / порогов → правка констант → **без** redeploy Layero.
4. Пустое свойство → временный файл на сервере + WARN `scoring=file` / `rating=file`.

## Путь поиска решения (lead-rating, 2026-07) — итог

1. `jsonval` + константа / маркетплейс-«Вебхук» → отказались для продакшена.
2. HTTPS API + кастомное активити на Layero (`apps/lead-rating-api`).
3. Зависание БП: POST без `access_token` → OAuth (`client_id`/`secret` + save-auth).
4. После деплоя снова зависание → **отдельный** входящий вебхук в `BITRIX_WEBHOOK_URL` (не общий с другими системами).
5. Запись рейтинга только при отличии → можно автозапуск на create/update без лишнего цикла.
6. **Результат:** БП `[AUTO] Категория клиента` стабильно считает и пишет «Рейтинг лида»; меню после деплоя не обязательно при заданном webhook.

Портал: `braincon.bitrix24.ru`. Веса/поля: `internal/lead-rating/`.

## Чеклист нового активити (копипаста)

1. Поднять HTTPS-сервис (**один preview-домен** для app handler и activity handler).
2. Сделать `/bitrix/install` + `/bitrix/handler` с BX24-fallback и **`/bitrix/save-auth`**.
3. Сделать `/bitrix/activity` → расчёт → **`bizproc.event.send` до HTTP-ответа**.
4. Создать **серверное** локальное приложение: urls handler/install (**не** activity), права `crm`+`bizproc`.
5. В хостинг: `BITRIX_CLIENT_ID` + `BITRIX_CLIENT_SECRET` (+ `PUBLIC_BASE_URL`); redeploy.
6. Сохранить → **Переустановить** → «Готово»; открыть пункт меню (сохранение OAuth).
7. Вставить активити в БП → остановить старые зависшие экземпляры → прогнать на тестовом документе.
8. При сбое смотреть `/bitrix/debug/last-activity`.
9. Дописать сюда новые грабли.
