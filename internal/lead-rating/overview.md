# БП: расчёт «Рейтинг лида» по полям категории клиента

**Статус:** работает на `braincon.bitrix24.ru` (2026-07)  
**Сущность:** Лид  
**Тариф:** Облако, Профессиональный  
**Результат:** поле `Рейтинг лида` (`UF_CRM_1783504656939`)  
**Runtime:** [`apps/lead-rating-api`](../../apps/lead-rating-api/README.md) + локальное приложение + отдельный вебхук в Layero  
**БП:** `[AUTO] Категория клиента` (create + update; запись рейтинга только при изменении)  
**Паттерн установки / грабли:** [`docs/bitrix-local-app-activity.md`](../../docs/bitrix-local-app-activity.md)

## Цель

По заполненным выпадающим спискам в блоке «Категория клиента» посчитать рейтинг лида как **среднее весов** выбранных значений (поля с «Нет данных» / пустые в среднее не входят).

## Поля-критерии (вход)

На момент проектирования:

| Поле | Роль |
|------|------|
| Сумма долга (Категория/сумма долга) | критерий |
| Готовность ко встрече | критерий |
| Готовность внести аванс | критерий |
| Платежеспособность | критерий |
| Контактность | критерий |

В каждом списке: **«Нет данных»** + несколько рабочих значений (сейчас по 4).  
Состав списков и набор значений **может меняться**.

Опционально отдельно (логика может отличаться от среднего): `Статус клиента`, `Обрушающие факторы` — зафиксировать отдельно, когда будет правило.

## Формула

```
Рейтинг = SUM(вес_i) / COUNT(вес_i)
```

где `вес_i` — только по полям с выбранным **рабочим** значением (не «Нет данных», не пусто).

Итоговый «Рейтинг лида» — либо само среднее (число), либо категория по порогам (константы порогов в БП/роботе).

---

## Как задать веса (главное решение)

### Не рекомендуется: словарь «значение → вес» только в константах БП

В облачном БП константы — скаляры (строка/число/дата), **не карта соответствий**.  
«Псевдо-словарь» через десятки констант и условий:

- плохо масштабируется при смене значений списков;
- усложняет перестройку, а не упрощает.

Константы БП оставить для **порогов итогового рейтинга** (например `>= 3.5 → Высокий`), не для всех значений всех списков.

### Рекомендуется: вес хранить при значении списка (XML_ID)

В настройках каждого значения списка (CRM → поля лида → значение перечисления) задать **XML_ID = вес** (`1`, `2`, `3`, `4` …).  
Для «Нет данных» — XML_ID пустой или `0` и **исключать** из среднего.

Плюсы:

- вес живёт вместе с данными поля;
- при добавлении значения сразу задаёте вес;
- БП/робот не хранит длинную таблицу соответствий.

Минус облака: в дизайнере БП удобнее оперировать **ID значения**, чем XML_ID. Поэтому на практике используют один из мостов ниже.

### Практичная схема для облака (без внешней разработки)

**Слой 1 — веса (скрытые числовые поля лида):**

| Служебное поле | Заполняется из |
|----------------|----------------|
| `Вес: сумма долга` | Сумма долга |
| `Вес: готовность ко встрече` | Готовность ко встрече |
| … | … |

При изменении списка — робот/ветка условий пишет число в парное поле веса (`Нет данных` → очистить вес).

**Слой 2 — среднее:**

Робот/БП:  
`Рейтинг лида = среднее по всем заполненным полям веса`.

Перестройка:

1. Добавили значение в список → дописали 1 условие «значение → вес».  
2. Добавили новый критерий → новое поле списка + парное поле веса + условие + включили в среднее.

### Альтернатива: справочник (смарт-процесс / список)

Элементы: `Код поля` + `ID/XML значения` + `Вес`.  
Гибко при частых изменениях, но в чистом облачном БП lookup тяжелее; чаще считают через приложение / Apps Script / вебхук.

Имеет смысл, если расчёт выносите во **внешний** контур (у вас уже есть `GasBitrixCoreLibrary`).

## Можно ли в начале БП задать «Значение → Вес» в константах?

**Как настоящий словарь — нет.**  
**Как упрощение при жёсткой шкале — частично да:**

- если во *всех* списках одинаковая шкала уровней (1…4) с одними и теми же весами,
- константы: `W1=1`, `W2=2`, `W3=3`, `W4=4`,
- в условиях маппите «порядок/смысл значения» на `W1…W4`.

Если у каждого списка своя семантика и свои веса — константы БП не спасут; держите веса у значений (XML_ID) или в таблице/скрытых полях.

## Рекомендуемый вариант для этого портала

1. Договориться о шкале весов (например 1–4).  
2. Прописать вес каждому рабочему значению каждого списка (таблица ниже).  
3. Реализовать через **скрытые числовые поля весов + среднее** (роботы/БП на лиде).  
4. Пороги итогового «Рейтинг лида» — в константах.  
5. «Нет данных» не участвует в среднем.
